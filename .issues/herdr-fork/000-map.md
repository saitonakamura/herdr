## Destination

Every box (both macs, fedora, WSL, windows) runs a herdr built from
`saitonakamura/herdr` and installed from `saitonakamura/homebrew-tap` (unix) or the
fork's release asset (windows). The fork carries the behaviour changes below, and
loom and the dotfiles work with every one of them.

## Notes

- Vocabulary: [`GLOSSARY.md`](../../GLOSSARY.md). Decisions with trade-offs:
  [`docs/adr/`](../../docs/adr/) 0001–0008. Fork rules: `FORK.md` (written by 001).
- **The live runtime.** herdr runs every agent pane, the one building it included.
  Never replace the installed binary, restart a herdr server or run `brew` against
  `herdr` without asking the user. Test builds against the debug `herdr-dev` server:
  `env -u HERDR_SOCKET_PATH -u HERDR_CLIENT_SOCKET_PATH cargo run -- <command>`, or a
  throwaway named session.
- **Break nothing.** loom (`~/dotfiles/.config/herdr/plugins/loom`, tests in
  `tests/run.sh`) and the dotfiles depend on herdr's CLI and API. A change that
  breaks them fixes them in the same change. A dotfiles change follows
  `~/dotfiles/CLAUDE.md` § cross-host reconciliation: docs fixed in the repo, one
  `.issues/herdr-fork/` ticket per box for on-box steps.
- **Upstream.** Fork-only. Never open issues, PRs or discussions on herdrdev/herdr.
  Keep changes small and neutrally named so periodic upstream merges stay cheap.
- **License.** Apache-2.0: keep `LICENSE` and notices in the fork and in release
  assets.
- **Rollout.** A behaviour change reaches the boxes as a new fork release
  (`<upstream>+fork.N`) and a `brew upgrade`; only the first cutover (003) has
  per-box tickets.
